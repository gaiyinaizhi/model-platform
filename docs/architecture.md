# 架构设计

> 2026-10-12 设计初稿，待实施。以下是待评审的逻辑设计，不表示已有服务、API、数据库表或已完成对接。

## 1. 目标与基本原则

`model-platform` 是独立的模型训练与交付工程，供 `visionlab`、教学平台、机器人和无人机等独立产品共同使用。共享算法和模型能力，不合并各产品的业务职责。

初期选择模块化 Python 工程，通过 API、Worker 和适配器形成最小可运行闭环。API 与 Worker 是逻辑职责，可以按需要运行在独立进程中；不预先承诺微服务拆分、某种队列、数据库或集群调度系统。

最先解决一个真实训练任务，而不是建设覆盖所有任务、设备和组织的 MLOps 平台。具体技术选型以首个切片的可验证需求为依据。

## 2. 系统边界

| 责任方 | 负责 | 与本工程的关系 |
| --- | --- | --- |
| 教学平台 | 课程、教学任务、成绩及教学接入协议 | 发起授权的模型任务，按教学协议消费结果 |
| `visionlab` | 独立的专业视觉实验与训练工作台 | 消费共享模型能力，与教学平台独立 |
| 机器人产品 | 业务应用、机器人控制与运行安全 | 消费经验证的模型或交付包 |
| 无人机产品 | 业务应用、飞控、飞行与设备安全 | 消费适配后的推理产物，不让本工程承担飞控闭环 |
| 业务后端，优先验证 Sluggard | 业务任务、归属、审批与界面；推荐主写权威模型登记和发布状态 | Sluggard 的实际能力与接口待核实，不预设已完成集成 |
| 资产管理边界（实现与可复用能力待核实） | 数据集及文件资源的稳定引用、访问与存储边界 | 有能力则复用；没有时只补最小资源引用与存储适配，不阻塞首个切片 |
| 本工程 | 算法执行、训练与评估事实、不可变技术清单、交付产物及技术回执 | 向业务后端幂等登记或关联结果，不另建完整模型登记业务 |

业务任务与执行任务不是同一对象：一个教学或业务任务可以关联多个训练或评估执行。本工程不复制业务任务的审批、成绩或业务状态机。

训练通常发生在服务器或训练服务中。端侧通常只负责推理；若未来需要端侧训练，应作为独立能力重新验证，不在当前范围内。

## 3. 核心领域对象

下表是概念模型。字段名称、序列化格式和存储方式尚未定稿，不应据此宣称已有 API。

| 对象 | 含义 | 必须保留的关键关系 |
| --- | --- | --- |
| `AlgorithmRecipe` | 一个版本化的算法执行配方，声明任务类型、输入契约、参数约束、入口和可用能力 | 配方版本、代码或实现来源、执行环境要求；不绑定课程或设备业务 |
| `DatasetVersion` 引用 | 经确认的数据管理边界内某一数据版本的稳定引用 | 资产 ID、版本、可取得时的内容摘要、数据契约与授权上下文；不在这里另建数据集目录 |
| `TrainingRun` | 一次逻辑训练请求，固定配方、数据、参数和执行要求 | 业务关联 ID、幂等键、输入快照、来源与结果引用 |
| 执行 attempt | 某个 `TrainingRun` 的一次实际执行尝试 | run ID、执行序号、运行器或外部任务 ID、状态、日志、心跳或时间、错误与检查点引用 |
| `Evaluation` | 一次针对特定模型或转换后产物的评估及其证据 | 被评估版本或产物摘要、评估数据版本、协议版本、环境、指标与限制 |
| `ModelVersion` | 由业务后端权威登记的模型版本，适用于自训、导入、厂商或 API 来源 | 来源、能力、版本标识、不可变技术清单及训练、评估或外部服务引用 |
| `TargetProfile` | 目标运行环境的版本化要求 | 运行时、格式、输入输出、架构、资源限制及验收条件；具体设备待选 |
| `DeploymentPackage` | 面向某一 `TargetProfile` 准备的可交付产物集合 | 模型版本、转换或量化配置、依赖、校验摘要、评估证据、使用说明 |
| 发布记录 | 业务后端主写某个包向指定环境或消费方的发布、交付或撤回状态 | 关联本工程技术回执，记录包版本、目标、授权和时间；区别“生成包”“交付成功”“运行验证” |

### 对象之间的关系

- 一个业务任务可以对应多个 run；一个 run 可以有多个 attempt
- 同一 run 的输入和配置保持不变；改变配方、数据或训练参数应创建新 run
- 重试会新增 attempt，不能覆盖历史失败；是否从检查点恢复需明确记录
- 一个 run 可以生成多个候选产物，只有通过既定登记条件的结果才成为模型版本
- 一个模型版本可以有多次评估，也可以针对多个目标生成不同交付包
- 转换或量化会生成新的派生产物及摘要，不覆盖原始权重；评估必须指向实际被测产物
- 一个包可以被交付多次，各次发布分别记录；生成包不等于已经部署到设备
- 模型、包和发布记录不得使用会被静默替换的“最新”指针作为唯一追溯依据

### 模型登记与技术清单的单一主写边界

目标是保持一份权威模型登记、一份不可变技术清单和明确的资产引用，不在业务后端、Python 执行工程与资产管理侧维护多套可独立编辑的同类记录。

建议的初始归属如下，需在第一阶段核实既有能力后确认：

1. 业务后端主写业务任务、权威模型登记和发布状态；优先验证 Sluggard 是否适合承担这些职责
2. 本工程主写训练执行、评估和派生关系，生成包含产物、摘要与版本引用的不可变技术清单，并提供发布技术回执
3. 业务登记通过稳定 ID 与技术清单关联，执行状态和指标只读展示；本工程不复制业务登记或发布审批状态机
4. 资产管理边界的实现与可复用能力待核实。有现成能力则复用；没有时只补稳定数据版本引用和受控存储适配，不以建设完整资产中心为前置条件
5. 技术清单引用资源 ID、版本与摘要，不把文件本体、可过期签名 URL 或凭据当作长期身份

如果已有业务或资产系统提供合适的模型登记能力，应优先复用；具体主写归属可在核实后调整，但 Python 执行层不默认另建完整登记业务。**实现写入接口前必须逐项确认主写方；不能边接入边双写。** 最小切片可以先使用明确的资源引用与存储适配，不等待完整资产平台建成。

本工程向业务后端提交技术清单并通过幂等登记关联。跨系统同步采用可重试的登记或查询过程，记录关联 ID、同步状态和错误并可对账。同步中的记录不能伪装成已登记、已发布或可交付。失败不通过无记录的手工覆盖来“修平”。

## 4. 多种模型来源与能力声明

| 来源 | 可记录的来源信息 | 不能默认成立的能力 |
| --- | --- | --- |
| 自训模型 | 配方、数据、run、attempt、环境和权重摘要 | 能导出到任意格式、能在任意设备运行 |
| 导入模型 | 提供方、原版本、导入时间、格式、摘要及使用条件 | 可继续训练、可转换、拥有完整训练血缘 |
| 厂商模型 | 厂商及版本、交付方式、使用限制与支持目标 | 允许改造、量化、再分发或离线部署 |
| 外部 API | 提供方、接口或模型标识、可取得的版本及调用约束 | 拥有本地权重、可以训练、可以导出、版本永不变化 |

能力至少区分训练、微调、评估、导出、转换、量化和目标运行支持。用“支持 / 不支持 / 待验证”表达已知程度，并附依据；不把缺少信息当成支持。

外部 API 可以登记为一种模型消费来源，但不强制生成虚假的权重或设备交付包。若未来交付调用适配配置，必须与离线模型包区分，凭据在使用环境解析，不打进包中。对无法锁定版本的远端服务，应记录这一限制，不能承诺可重复结果。

## 5. 初期模块划分

以下是逻辑模块，不是当前已有目录，也不是必须独立部署的服务：

- **领域与契约**：核心对象、状态转换、输入校验、版本关系与能力判断
- **API**：认证授权、提交与查询、幂等处理、取消请求；不在请求进程内承担长时间训练
- **执行 Worker**：领取执行、调用配方或外部训练服务、记录 attempt、采集日志与输出
- **评估与交付**：评估协议、转换与量化步骤、目标验证、产物清单和发布技术回执
- **适配器**：隔离 Sluggard、可复用的资产管理能力、存储、执行服务、模型提供方及未来设备的具体接口

可考虑在真实实现时采用 `src/` 和 `tests/`，但目前不创建无实现的目录、类或插件框架。模块之间先用清晰的 Python 接口隔离；新增队列或外部调度器时仍复用领域契约。

API 框架、持久化方案、队列与运行环境均未锁定。即使首版使用单机 Worker，也需要保存执行状态并定义中断恢复方式；不依赖进程内变量作为唯一事实来源。

## 6. 异步执行与可靠性

### 提交与幂等

- 接收任务前校验配方能力、数据权限、参数和目标要求
- 幂等键按调用方或项目隔离，并绑定请求内容摘要；同键同内容返回同一结果，同键不同内容明确冲突
- 业务任务 ID 用于关联，不直接假定为执行唯一键，一个业务任务允许多次实验
- 提交记录与工作领取之间应有可恢复的交接机制，避免“已答应但任务丢失”；具体实现随持久化方案选定

### 执行状态与取消

建议至少覆盖排队、运行中、取消请求中、成功、失败和已取消等语义。run 反映逻辑请求进度，attempt 反映一次实际执行；具体状态名和转换条件在契约阶段确认。

- 取消是请求，收到请求不等于执行已停止；记录实际停止结果与不支持取消的限制
- 重复领取或消息重放不能让同一个 attempt 重复发布结果；使用所有权、租约或等效机制防止过期 Worker 写回
- attempt 失败后，按明确策略决定是否重试、恢复检查点或结束 run
- 仅对可重试错误进行有上限、有退避的自动重试；数据错误、权限错误和确定性代码错误不应盲目重试
- 外部训练服务超时后先查询原任务状态，避免重复提交昂贵的训练任务
- 取消与完成竞态、晚到回调和重复回调必须有一致的处理规则，终态不能被旧消息随意覆盖

### 恢复与对账

持久化任务关联、外部执行 ID、状态时间和必要的心跳信息。进程重启后检查未完成记录及实际执行状态，区分仍运行、可恢复、失联和需要人工判断的任务。

产物写入、技术登记与状态更新未必处于同一事务，需通过稳定 ID、校验摘要、可重试步骤和对账发现部分完成。对账不得擅自删除数据或重跑付费作业；可能增加成本的恢复需符合已授权的任务限制。

## 7. 可追溯性与交付验收

每条结果链应能回答：使用什么配方和数据，在哪个代码与环境下，以什么参数运行，经历哪些 attempt，评估了哪一个具体产物，最终交付给哪个目标。

至少记录：

- 配方版本、代码提交或外部实现版本、训练配置及可用的随机种子
- 数据版本与划分约定、内容摘要或不能提供摘要的原因
- 执行环境和必要的依赖信息、硬件或外部服务标识
- 原始模型及派生产物的不可变摘要、转换工具与配置
- 评估协议、指标定义、评估环境、原始结果引用和已知限制
- 目标配置版本、交付包版本、发布对象与回执

这些记录提高可复现性，不保证不同硬件、非确定性算子或不可固定版本的外部服务产生完全一致结果。

转换和量化后的模型必须按实际交付产物验证。验收关注任务质量、输入输出一致性、格式与运行时兼容、延迟、内存等资源占用；具体阈值、测试负载和设备条件在选定 `TargetProfile` 时确定。服务器上的验证不等于真实机器人或无人机上的设备验证。

## 8. 安全与权限

- 调用、数据读取、执行、登记、下载和发布分别校验授权，不能只信任请求里的项目或业务 ID
- Worker 只获取当前任务所需的最小数据和存储权限，使用受控凭据引用，避免凭据进入日志和模型包
- 数据集、模型、导入包和算法配方均视为需要校验的输入；不要在高权限 API 进程中直接加载不可信可执行内容
- 真实数据和权重保存在授权存储中，不进入 Git；跨项目访问和敏感数据传输需遵守来源系统权限
- 对提交、取消、登记、发布与权限相关操作保留必要审计信息，并对敏感日志做过滤
- 引入模型前确认使用、训练、转换和再分发限制；来源不清不等同于可自由使用

## 9. 待确认决策

1. 首个任务、算法配方、数据版本、运行资源及可验收质量指标
2. 可复用的资产管理与模型登记能力是否存在；没有时的最小引用、存储适配方案，以及每类记录的唯一主写方
3. Sluggard 的实际可复用能力、业务任务归属、鉴权和对接契约
4. 最小 API、持久化、任务交接和执行环境方案
5. 首个推理输出目标与转换需求；机器人和无人机具体设备另行验证
6. 交付、发布与设备侧安装的责任边界，发布授权及失败恢复方式
