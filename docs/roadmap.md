# 实施路线

> 2026-10-12 设计初稿。除基础文档与忽略规则外，下列工程能力均未实施；顺序代表依赖关系，不构成交付日期承诺。

## 推进原则

- 先完成一个可验证的真实切片，再扩展模型来源、业务接入和设备
- 业务管理与资产能力的实现情况待核实；有则复用，没有时只补最小必要能力，不重复建设完整后台或资产中心
- mock 用于契约演示与故障场景验证，真实模型与设备能力需要独立证据
- 每阶段留下明确验收结果；没有达到条件就不把能力标为完成

## 阶段 0：基础设计与范围确认

**当前状态：设计文档初稿，待评审。**

交付物：

- 仓库定位、架构边界、核心对象和协作约定
- 当前能力与规划能力的明确区分
- 首个切片之前必须确认的决策清单

完成条件：相关负责人确认底层不承担教学业务、机器人控制与飞控安全；确认 `visionlab` 与教学平台各自独立，以本工程共享模型训练、评估、交付与推理服务运行能力，区分后端持续 API、端侧运行包与外部 endpoint 适配。

## 阶段 1：核实已有系统，收敛最小契约

**当前状态：待开始。**

工作：

- 核实 Sluggard 能力与可用接口，判断它适合承担哪些业务管理职责
- 核实资产管理边界的实现与可复用能力；没有现成能力时确定最小资源引用与存储适配，不以完整资产中心为前置条件
- 确定唯一主写方：推荐业务后端主写业务权限、模型登记、部署期望与发布审批，本工程保存执行、评估事实、不可变技术清单及实际实例的 ready/健康观察状态，通过稳定 ID 与幂等过程关联
- 选定一个算法配方、可合法使用的数据版本、训练执行环境和推理输出目标
- 定义最小提交、查询、取消与结果读取契约，明确鉴权、业务关联和错误语义
- 明确 `ModelService` 接口与版本关系、`ServingDeployment` 期望修订和实际运行记录；区分有终态任务与持续服务，约定 ready/健康及状态对账语义
- 确定最低限度的 API、持久化、Worker 和任务交接方案

验收条件：

- 输入、输出、责任方和权限边界可评审，没有假设已存在的第三方 API
- 模型登记、产物清单、部署期望与实际运行观察分别有唯一主写方，没有双写来源
- 数据与运行资源可实际访问；质量、资源和输出验收方式已确定
- 若仍有关键条件缺失，明确阻塞，先完成不依赖它的文档或契约工作

## 阶段 2：最小执行骨架与契约演示

**当前状态：待开始。**

工作：

- 创建有实际用途的 Python 模块、配置入口与测试
- 实现可持久化的 run / attempt 记录、查询和最小 Worker 流程
- 用明确标注的 mock 验证提交、完成、失败、取消和结果关联
- 验证幂等、重复消息与基础重启恢复；为真实适配器保留清晰边界

验收条件：

- 有可重复的开发和测试步骤，命令经过实际执行
- 同一幂等请求不重复创建 run；重试 attempt 不丢失历史
- 任务中断后能识别状态并恢复处理或准确报告待对账
- 演示明确标为 mock，不宣称完成真实训练、真实评估或设备支持

这一阶段只做支撑首个真实切片所需的骨架，不扩展为通用编排平台。

## 阶段 3：首个真实端到端切片

**当前状态：待开始。**

闭环：

`一个 AlgorithmRecipe → 一个 DatasetVersion 引用 → 真实 TrainingRun → Evaluation → ModelVersion → 一个 TargetProfile 的输出`

工作：

- 接入真实算法执行和数据读取，记录输入、代码、配置与环境
- 运行真实训练及约定评估，保留可复核的输出和错误记录
- 生成不可变技术清单，按已确认的主写边界向业务后端幂等登记并关联模型版本
- 准备第一个目标的交付包，并验证加载、推理、输入输出和目标相关指标
- 若使用转换或量化，保留派生链，并对转换后的产物重新评估

验收条件：

- 真实完成上述链路，能从交付产物追溯到配方、数据、run、attempt 和评估
- 不使用 mock 指标、假训练日志或未验证的设备说明代替结果
- 达到事先约定的质量与资源标准；未达标时保留记录并明确原因
- 至少验证失败重试、取消和执行中断等适用异常路径，披露未覆盖情况
- 结果可由另一位开发者按说明复核；非确定性与环境限制如实记录

首个 `TargetProfile` 可以是明确的服务器推理环境，不因此宣称机器人或无人机实机可用。交付包生成完成也不等于已经向生产或设备发布。

## 阶段 3A：首个持续推理服务

**当前状态：待开始，依赖阶段 3 的真实训练与经验证交付包。**

工作：

- 在一个明确的 CPU 或服务器环境运行该真实交付包，提供最小持续模型 API；不要求此时建设 Kubernetes 或通用路由编排
- 建立逻辑服务、版本化预后处理与输入输出契约，以及实际部署或实例记录，关联模型、包、runtime、资源和 endpoint
- 接收获批的部署期望并观察真实运行状态，验证加载、健康、ready 与实际调用；业务后端只展示运行事实投影
- 与训练 Worker 隔离资源，验证同机训练不会无约束挤占推理的 GPU、显存或其他资源
- 验证鉴权、请求限额、输入校验与错误语义；大视频选择受控引用或授权直连路径，不强制 Sluggard 转发

验收条件：

- 服务持续运行并能真实调用，结果可追溯到实际模型或包及接口契约版本；训练完成、包验收、加载成功与服务 ready 分别有证据
- 加载失败、调用失败、健康异常或状态过期可准确报告；未 ready 的实例不能接收推理流量
- 进程重启后能对账实际版本并重新验证就绪；停用后不再接收新调用，记录在途请求处理和实际停止结果
- 启动、停用、更新和回滚均有真实验证，版本切换不能路由到未 ready 实例；部署期望和观察状态无冲突双写
- 资源和最小真实负载达到约定标准，披露未覆盖场景；服务器服务就绪不等于端侧设备验收

本阶段不以外部厂商 endpoint 调用或 mock 替代自有真实包的服务运行验收；外部适配另按来源能力验证。

## 阶段 4：分别接入 visionlab 与教学平台

**当前状态：待开始，依赖真实切片稳定；持续 API 接入还依赖阶段 3A 验收。**

工作：

- `visionlab` 作为独立专业视觉实验与训练工作台，接入共享训练与模型消费能力
- 教学平台独立定义课程、教学任务、成绩及教学接入协议，再按协议接入模型能力
- 在业务后端创建和管理各自业务任务，通过稳定 ID 关联执行；Sluggard 优先验证
- 展示训练进度、失败原因、评估结果与可用模型；使用持续 API 时展示真实服务版本、ready/健康状态与观察时间
- 验证权限隔离、重复操作、取消与状态同步

验收条件：分别按选定的专业视觉实验场景和教学场景验收，能通过各自业务入口发起并查看结果；`visionlab` 与教学平台保持独立，课程、成绩与教学规则由教学平台负责；业务登记、部署期望与审批、执行及服务运行事实各有唯一主写方。模型 API 契约由本工程维护，业务 API、成绩与告警规则由相应业务产品负责。

## 阶段 5：设备适配与模型来源扩展

**当前状态：待开始，范围按真实需求选择。**

工作按需求分支推进，不要求同时完成：

- 选定无人机或机器人设备与运行时，建立版本化 `TargetProfile`
- 按设备需要增加转换、量化和交付适配，并执行实机验收
- 根据实际场景接入导入模型、厂商模型或外部 API，逐项验证能力与使用限制
- 在业务产品和设备负责人参与下确认发布、回退及安装边界

验收条件：

- 设备结论来自选定版本和真实测试条件，包含质量、延迟、内存等相关结果
- 产物、测试证据与目标配置可追溯；服务器模拟结果与实机结果分开标注
- 对不支持的训练、导出、转换或离线部署能力给出明确限制；外部 endpoint 适配不冒充本地部署或离线包
- 发布有授权和回执；设备安装、控制及安全验收仍由对应产品负责

## 暂不提前建设

- 多租户计费、模型市场、通用可视化工作流和实验门户
- 多集群调度、全自动超参搜索或无实际需求的微服务拆分
- 自建数据集资产中心、课程系统、机器人控制或飞控系统
- 未选型设备的通用兼容承诺，或“支持所有模型格式”的抽象框架

只有出现明确使用者、具体问题和验收标准后，才评估这些扩展。

## 下一步需要决定什么

1. 首个算法任务与数据版本是什么？
2. 谁能提供真实训练资源和结果验收标准？
3. 可复用的资产与模型登记能力是否存在？若没有，最小引用、存储适配及业务登记由谁负责？
4. Sluggard 当前能提供什么接口，业务系统接入由谁确认？
5. 首个交付目标采用哪种推理环境，是否确实需要模型转换？
6. 首个持续服务如何定义接口版本、ready/健康、资源隔离和数据访问路径，启停、更新与回滚如何验收？

这些问题决定第一批实现工作，不需要在初始化时一次选定所有设备和基础设施。
